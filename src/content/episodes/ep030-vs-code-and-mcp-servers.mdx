## Summary

A solo demo answering a viewer question: people had seen the MCP server driven from Azure DevOps and GitHub, and wanted to see it running on their own desktop. Mike wires the Power BI modeling MCP server into VS Code, enables it from the chat settings, refreshes the tool list, and connects an agent to a semantic model open in Power BI Desktop. Being explicit in the prompt turns out to matter -- naming the target, the server, and the file name is what makes the connection reliable. The agent then lists measures, proposes sales and time-intelligence measures, marks the date table, and files everything into the right display folders, with a detour to push the model's date range forward so year-over-year calculations resolve. The second half repeats the exercise against a model hosted in powerbi.com, where authentication kicks in and the agent needs the workspace and model names spelled out rather than just the URL.

## Key Takeaways

- ▸ The Power BI MCP modeling server is enabled per session from the chat settings icon in VS Code, and the tool list needs refreshing before the agent can see what the server offers.
- ▸ If the server is missing from that menu, install the Power BI MCP Modeling Server extension from the VS Code marketplace first.
- ▸ Explicit prompts are what make the connection reliable: name the target, name the MCP modeling server, and name the file.
- ▸ Autopilot approvals stop the per-tool-call permission prompts, which is worth turning on once you trust what the agent is doing in a session.
- ▸ Pasting a powerbi.com URL is not enough -- the XMLA endpoint needs the workspace name and model name given explicitly.
- ▸ The agent proposed useful measures and marked the date table, but its output still needs reviewing; a stale date range in the model quietly broke the time-intelligence calculations until it was fixed.
