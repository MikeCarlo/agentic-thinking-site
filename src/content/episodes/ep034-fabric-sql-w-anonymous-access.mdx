## Summary

Friday demo night: Mike and Matthias try to build a public intake form as a Fabric app that uses Microsoft's new anonymous data access so an unauthenticated visitor can write name, title, and email into a Fabric SQL database. After a short news pass on Grokbot versus Claude agent teams, Mike scaffolds a repo in VS Code, creates a blank Fabric app, walks the official anonymous-role docs, and lets GitHub Copilot on Opus 4.6 implement a Rayfin schema with an anonymous `create` permission. `npx rayfin up` deploys the app and creates the table, but submitting the public form returns a GraphQL internal server error even after the tenant setting is enabled, extra logging is added, and sign-in is put back on a header. They run out of time with the form still broken, commit to circling back with Microsoft, and call out the lesson of committing after each working step.

## Key Takeaways

- ▸ Anonymous data access on Fabric apps is not "no auth." It is an extra role so unauthenticated users can be granted specific data operations such as read or create.
- ▸ The docs put `anonymous` and `authenticated` roles on the data entity and let you attach an array of permissions. Mike's target for a public form is read plus create on anonymous.
- ▸ Paste current Microsoft Learn into the prompt. Agents are trained on stale data and will miss a feature that shipped about a week ago.
- ▸ Rayfin pushes only the `dist` bundle to Fabric. After schema changes you need `npx rayfin up`, and a new SQL database should have its max vCores turned down for small-capacity demos.
- ▸ A GraphQL internal server error on submit can persist even with the tenant anonymous setting on and with a signed-in user. The live demo did not isolate whether that was a role bug, a wrong database binding, or a service issue.
- ▸ Commit after the authenticated template works, before the agent starts editing. One accidental implement click and a missing commit made it hard to walk the change back.
