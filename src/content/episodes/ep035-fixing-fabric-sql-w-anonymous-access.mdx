## Summary

Mike records a short cleanup after the live episode 34 demo, where the anonymous Fabric intake form failed with a GraphQL error. The GraphQL item is created behind the scenes when a Fabric app deploys and does not show as its own workspace artifact, which made the failure look mysterious. In the Rayfin schema, the agent's anonymous role had only `create`. That permission set does not work; the working pattern is an array with `read` first, then `create`. After `npx rayfin up` and a signed-out submit, a third test row lands in the Fabric SQL table, and the public form can write into Fabric without a signed-in user.

## Key Takeaways

- ▸ The GraphQL error on an anonymous Fabric app is often a data-role problem, not a missing GraphQL item in the workspace. The endpoint is bundled behind the app.
- ▸ An anonymous role with only `create` fails. Put both permissions on the role, with `read` first and then `create`.
- ▸ After changing the Rayfin schema, run `npx rayfin up` so the local bundle is pushed into the service before you retest.
- ▸ Prove anonymous access from the public app URL while signed out, then confirm the new row in the Fabric SQL table.
- ▸ Once the form writes to Fabric SQL, the rest of the Fabric stack — notebooks, stored procedures, semantic models, reports — can sit on that same incoming data.
- ▸ This is the fix for last Friday's live demo, not a new app. The intake form was already built; only the anonymous permissions were wrong.
