## Summary

Mike and Mathias take the manufacturing idea of a lights-out factory and ask what the software version looks like, then whether Power BI reports are close to one. Mathias draws a line between a small change on an existing model, which he thinks can be automated today, and a request that pulls in a new data source, where connection, auth, and staging choices are still too open for a single prompt. They spend the rest of the episode on the pieces that would make a report factory real: PBIR and TMDL as editable bricks, Omarchy as an operating system with an agent and debug skills built in, and the missing Fabric equivalents of hot reload and incremental publish.

## Key Takeaways

- ▸ A dark factory is an assembly line with requirements, bugs, and ideas on one end and shippable software on the other, with humans out of the turn-by-turn prompting loop. A harness is only one block inside that line.
- ▸ Iterating an existing Fabric setup — a new page, a visual, or a measure on a model you already understand — is close to fully automatable. Bringing in a data source you have never seen is not, because auth, live versus staged, and secrets open a much larger decision tree.
- ▸ PBIR and TMDL are the formats that make incremental report and model edits possible for an agent. Mike's challenge to the community is to learn those formats instead of treating the report as a binary.
- ▸ Omarchy is a Linux setup with a default agent, keyboard-first use, and packaged skills that file a GitHub issue or debug a failure from inside the OS. The analogy for Fabric is a skill that writes the bug the way an agent can act on it.
- ▸ Publishing a thin report and embedding it back in the browser can be the dev loop when you are not on Power BI Desktop, but Desktop Bridge still rerenders the whole report. What they want is Vite-style hot reload and incremental PBIR publish so a one-visual change does not upload hundreds of files.
